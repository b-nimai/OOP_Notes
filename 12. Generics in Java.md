# Generics in Java

> **One-liner:** Parameterize types — write one class/method/interface that works for many types while the **compiler** enforces type safety, so no casts and no `ClassCastException`.

**Trigger phrase:** *"`<T>` is a type placeholder filled in at use-site — compile-time type checking, no casting; bounded `<T extends Number>` restricts, wildcards `? extends`/`? super` flex method params; all erased to `Object` at runtime (type erasure)."*

---

## Core Idea
Generics (Java 5+) let a class/method declare a **type parameter** `<T>` that the caller fills in. The compiler then checks every use against that type, so mistakes are caught at **compile time** instead of blowing up at runtime.

```java
// Before generics — raw, unsafe:
ArrayList list = new ArrayList();
list.add("Hello");
list.add(100);                       // compiles fine — different types mixed!
String s = (String) list.get(0);     // cast required everywhere; risky

// With generics — safe:
ArrayList<String> list = new ArrayList<>();
list.add("Hello");
list.add(100);                       // ✗ compile-time error
String s = list.get(0);              // no cast — compiler knows it's a String
```

**Why it matters:** **type safety** (catch errors at compile time, not runtime) · **no casting** (cleaner, less error-prone) · **reusability** (one definition, many types) · less duplicated code.

> **Mental model:** `<T>` is a **blank** the compiler fills in and then polices. It exists only while compiling — see [Type Erasure](#type-erasure).

**Naming convention (by convention, not rule):** `T` = Type, `E` = Element, `K` = Key, `V` = Value, `N` = Number.

---

## Generic Class
A class with one (or more) type parameters declared after the name. Same code serves every type.
```java
class Box<T> {                 // T = the data type, chosen by the caller
    private T value;
    public void set(T value) { this.value = value; }
    public T get() { return value; }
}

Box<Integer> intBox = new Box<>();   intBox.set(100);
Box<String>  strBox = new Box<>();   strBox.set("Hello");
```
Multiple params are allowed: `class Pair<K, V> { K key; V value; }`.
- **Key point:** one class, any type → no separate `IntBox`, `StringBox`, etc.

## Generic Method
A method with its **own** type parameter, declared **before the return type**. Independent of whether the class is generic.
```java
class Util {
    public <T> void print(T data) {          // <T> declared here
        System.out.println("Data: " + data);
    }
}

obj.print(100);        // T = Integer
obj.print("Generics"); // T = String
obj.print(3.14);       // T = Double
```
- **Key point:** replaces method **overloading** — one method handles all types.
- ⚠️ **Must declare the parameter** (`<T>`) either on the class or before the method's return type. Skip it and the compiler treats `T` as an unknown symbol → **compile error**.

## Bounded Type Parameters — `<T extends X>`
Restrict what `T` can be, so you can **call that type's methods** safely.
```java
class NumericBox<T extends Number> {     // T must be Number or a subclass
    private T num;
    public NumericBox(T num) { this.num = num; }
    public double square() {
        return num.doubleValue() * num.doubleValue();  // doubleValue() exists ⇒ Number is guaranteed
    }
}

new NumericBox<Integer>(10);     // ✓ Integer extends Number
new NumericBox<Double>(5.5);     // ✓ Double  extends Number
new NumericBox<String>("Hi");    // ✗ compile error — String is not a Number
```
- `extends` here means **"is or extends"** — works for both classes **and** interfaces (`<T extends Comparable<T>>`).
- Multiple bounds: `<T extends Number & Comparable<T>>` (class first, then interfaces).
- **Why:** without the bound, `T` is just `Object` and you could only call `Object` methods.

## Wildcards — `?` (unknown type)
Used in **method parameters** when the exact type parameter doesn't matter — adds flexibility a fixed `T` can't.

| Wildcard | Name | Read? | Write? | Use when |
|----------|------|-------|--------|----------|
| `? extends T` | **Upper** bounded | ✅ read as `T` | ❌ (except `null`) | you **consume/read** from the structure |
| `? super T` | **Lower** bounded | ❌ (only as `Object`) | ✅ write `T` | you **produce/add** into the structure |
| `?` | Unbounded | as `Object` | ❌ | type truly irrelevant |

**PECS — "Producer `extends`, Consumer `super`."** If the collection *produces* values you read → `extends`. If it *consumes* values you add → `super`.

**Upper bound `? extends T`** — read-only view of `T` or its subtypes:
```java
static void printList(List<? extends Number> list) {
    for (Number n : list) System.out.print(n + " ");  // reading OK
    // list.add(10);   ✗ can't add — exact subtype unknown (could be List<Double>)
}
printList(List.of(1, 2, 3));        // List<Integer> ✓
printList(List.of(1.1, 2.2));       // List<Double>  ✓
```

**Lower bound `? super T`** — write-only-ish; add `T` safely:
```java
static void addNumbers(List<? super Integer> list) {
    list.add(10); list.add(20);     // adding Integer OK
    // Integer x = list.get(0);     ✗ could be List<Number>/List<Object> — read only as Object
}
addNumbers(new ArrayList<Number>()); // ✓ Number is a supertype of Integer
addNumbers(new ArrayList<Object>()); // ✓ Object too
```

## Raw Types — don't
Using a generic class **without** its type parameter (`Box` instead of `Box<String>`). Allowed only for backward compatibility with pre-Java-5 code.
```java
Box rawBox = new Box();     // raw — no type checking
rawBox.set("Hello");
rawBox.set(100);            // compiles, but mixes types → runtime trouble

Box<Integer> intBox = rawBox;  // unchecked-warning; later get() can throw ClassCastException
```
- **Problem:** reintroduces exactly the unsafe, cast-heavy, `ClassCastException`-prone behavior generics removed. The compiler only emits an **unchecked warning**, not an error.
- **Rule:** never use raw types in new code — always supply the type parameter (use `Box<Object>` if you genuinely need "any type").

## Type Erasure
The compiler **removes** all generic type info after type-checking; at **runtime** `<T>` is gone. This is how generics stay backward-compatible with pre-Java-5 bytecode.
```java
class Box<T> {  T value;  void set(T v){ value=v; }  T get(){ return value; } }
//  ▼ after compilation (erased):
class Box {     Object value;  void set(Object v){ value=v; }  Object get(){ return value; } }
```
- Unbounded `T` → replaced with **`Object`**; bounded `<T extends Number>` → replaced with the **bound** (`Number`).
- The compiler inserts casts for you where needed, so it still *looks* type-safe.

**Reasons:** backward compatibility · no runtime overhead · simpler JVM/bytecode.

**Consequences (interview favorites)** — because the type is gone at runtime you **cannot**:
- `if (obj instanceof T)` — ✗ type unknown at runtime.
- `new T()` / `new T[10]` — ✗ can't instantiate or make a generic array.
- Overload on erased signatures — `void f(List<String>)` and `void f(List<Integer>)` clash (both erase to `List`).
- Have a `static` field of type `T`.

## Interview Q&A (memorize)
1. **Why generics?** Compile-time type safety + reusability + no casting (no `ClassCastException`).
2. **Generic class vs generic method?** Class declares `<T>` after the name (whole class); method declares its own `<T>` before the return type (just that call).
3. **`<T extends Number>` vs `<? extends Number>`?** First defines a **type parameter** with a bound (on class/method); second is a **wildcard** used in a parameter for an unknown subtype.
4. **PECS?** Producer → `? extends`, Consumer → `? super`. `extends` = read, `super` = write.
5. **What is type erasure?** Generic types are stripped at compile time → replaced by `Object`/bound; nothing about `T` survives to runtime.
6. **Why can't you do `new T()` or `T[]`?** Type erasure — the runtime doesn't know what `T` is.
7. **Raw type?** Generic used without `<...>`; legal but unsafe (unchecked warnings) — avoid.

## Pitfalls
- **Forgetting to declare `<T>`** on the class/method → compiler can't resolve `T` (compile error).
- **Trying to `add` through `? extends T`** — upper-bounded wildcards are effectively read-only.
- **Raw types** — silently drop type safety; the warning is easy to ignore.
- **Expecting `T` at runtime** — `instanceof T`, `new T()`, generic arrays all fail due to **type erasure**.
- **Primitives aren't allowed** — `List<int>` ✗; use wrappers `List<Integer>` (autoboxing handles conversion).
- **`List<Object>` ≠ `List<String>`** — generics are **invariant**; `List<String>` is *not* a subtype of `List<Object>` (that's why wildcards exist).
