# Inheritance

> **One-liner:** A subclass (`extends`) reuses + extends + overrides the fields/methods of a superclass — code reuse via an **"is-a"** hierarchy.

**Trigger phrase:** *"child `extends` parent → inherits its members for free, adds its own, can override; reach for it on an 'is-a' relationship (Dog is-a Animal)."*

---

## Core Idea
- **Superclass (parent/base):** the blueprint holding shared attributes + behaviors.
- **Subclass (child):** `extends` the parent → can **reuse**, **extend** (add new), or **override** (specialize) inherited members.
- Test before using it: say **"child *is-a* parent"** out loud. If that's false, prefer composition.

```java
class School { void printSchoolName(){ System.out.println("DPS"); } }
class Student extends School {           // Student is-a School
    void printStudentName(){ System.out.println("Raj"); }
}
new Student().printSchoolName();          // ✔️ inherited for free
```

## 3 Types (class inheritance in Java)
| Type | Shape | Example |
|---|---|---|
| **Single** | A → B (one-to-one) | `Dog extends Animal` |
| **Multilevel** | A → B → C (chain; middle is child *and* parent) | `Animal → Mammal → Dog` |
| **Hierarchical** | A → B, A → C (one-to-many) | `Dog extends Animal`, `Cat extends Animal` |

> **Multiple inheritance** (one class extends *two* parents) is **NOT allowed with classes** in Java → see Diamond Problem below. Allowed via **interfaces**.

## Why use it (4 wins)
**Reusability** (don't rewrite shared code) · **Modularity** (concerns split per class) · **Extensibility** (add features without touching the base) · **Maintainability** (fix shared logic in one place).

## 3 Concepts that ride along
1. **Access modifiers** — `protected` members flow into subclasses; `private` does not. → [2. Access Modifiers](2.%20Access%20Modifiers.md)
2. **Method Overriding** — subclass redefines a parent method (same name + params + return type). Rules: can't tighten access modifier; only `public`/`protected` (inheritable) methods; use `@Override`. Enables **runtime polymorphism**. → [4. Polymorphism](4.%20Polymorphism.md)
3. **`super` keyword** — (a) access a shadowed parent member, (b) call the parent constructor `super(...)` to init inherited state.

## Overloading vs Overriding (classic interview trap)
| | **Overloading** | **Overriding** |
|---|---|---|
| Where | Same class | Parent ↔ subclass |
| Needs inheritance? | No | **Yes** |
| Params | **Must differ** (count/type/order) | **Must be identical** |
| Return type | Can differ | Must match (or covariant) |
| Access modifier | Anything | **Can't be more restrictive** than parent |
| Binding | Compile-time (static) | Runtime (dynamic) |

## The Diamond Problem (why no multiple class inheritance)
If `B` and `C` both extend `A` and override `method()`, and `D` extends both `B` and `C` — **which `method()` does `D` get?** Ambiguous. Java bans multiple **class** inheritance to avoid it. **Interfaces** sidestep it: they declare signatures (no conflicting bodies), so combining many is safe.

## Pitfalls
- **Inheritance ≠ default tool.** Overusing it for code reuse (when it's not a true *is-a*) creates rigid, tightly-coupled hierarchies — **prefer composition** ("has-a") when in doubt.
- **`private` members aren't inherited's interface** — they exist in the object but the subclass can't touch them directly; go through `protected`/getters.
- **Constructors aren't inherited** — a subclass must call `super(...)` (implicitly or explicitly) to build the parent part.
- **C++ contrast:** C++ *does* allow multiple class inheritance (and handles the diamond with `virtual` inheritance) — don't assume Java's "interfaces only" rule there.
