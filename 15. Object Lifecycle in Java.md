# Object Lifecycle in Java

> **One-liner:** The stages an object goes through — **Creation → Usage → (becomes unreachable) → Garbage Collection → Destruction** — managed automatically by the JVM, which reclaims memory once nothing references the object.

**Trigger phrase:** *"`new` allocates on the **heap**, reference lives on the **stack**; when no live reference can reach the object it's **eligible for GC**; Java uses **reachability** (Mark-Sweep-Compact), not reference counting, so it handles cyclic references; leaks come from lingering references (static/collections/listeners), not the GC failing."*

---

## Core Idea
Every object passes through a lifecycle: **Creation → Usage → Garbage Collection → Destruction.** Unlike C/C++, you never `free`/`delete` — the JVM's **garbage collector** automatically destroys objects once they're **unreachable** and reclaims their memory. Understanding *when* an object becomes unreachable is the key to avoiding **memory leaks**.

| Stage | What happens |
|-------|--------------|
| **Creation** | `new` allocates memory on the **heap**; the reference variable (on the **stack**) points to it |
| **Usage** | methods/fields accessed through the reference |
| **Eligible for GC** | no live reference can reach the object anymore |
| **Destruction** | GC reclaims the heap memory |

```java
class Demo { void performTask() { System.out.println("Task performed"); } }

public static void main(String[] args) {
    Demo obj = new Demo();   // obj → stack; new Demo() → heap
    obj.performTask();
}   // main ends → obj out of scope → Demo object unreachable → eligible for GC
```

> **Stack vs heap:** the **reference** (`obj`) sits on the stack and dies with its scope; the **object** lives on the heap until GC. Many references can point to one heap object.

---

## Object Creation
`new` allocates heap memory and runs the constructor; the reference variable points at that location.
```java
class Student { String name; Student(String name) { this.name = name; } }

Student s = new Student("Raj");   // heap allocation + constructor; s points to it
```

## When does an object become eligible for GC?
**When no live thread can reach it** — i.e. it falls out of the reference graph. Common triggers:
```java
A a1 = new A();   // object created
A a2 = a1;        // two references to the same object
a1 = null;        // one reference left → still reachable
a2 = null;        // zero references → now unreachable → eligible for GC
```
Other ways: reference reassigned to a new object, or it simply goes **out of scope** (method returns).

---

## Reference Counting vs Reachability — why Java picks reachability
**Reference counting** (each object tracks how many references point to it; free when count hits 0) is a *conceptual* aid, but **Java does NOT use it.**
- Java uses **reachability-based GC**: starting from a **root set** (local vars, static fields, active threads), it traverses the object graph (e.g. **Mark-and-Sweep**) and keeps only what's reachable.
- **Why not reference counting?** It **can't reclaim cyclic references** — two objects pointing at each other keep counts ≥ 1 forever even when unreachable. Reachability handles cycles correctly (see [Cyclic References](#cyclic-references)).

---

## Garbage Collection process (Mark → Sweep → Compact)
GC isn't one algorithm — multiple collectors (Serial, G1, ZGC, Shenandoah) exist — but the core phases are:
1. **Mark** — start from the root set, traverse the object graph, **flag every reachable object**.
2. **Sweep** — scan the heap; objects left **unmarked** are unreachable → **delete them, reclaim memory**.
3. **Compact** — move surviving objects together to remove **fragmentation** (gaps), improving allocation speed and cache locality. *(Not every collector compacts; G1 works on regions.)*

**Stop-the-World (STW) pauses:** the heap isn't thread-safe, so the JVM **freezes application threads** during sensitive phases (marking/compacting) to avoid corruption. Modern collectors (G1, ZGC, Shenandoah) **minimize** but can't fully eliminate pauses.

**`System.gc()`** — only a **request** to run GC, not a command; the JVM may ignore it. **Don't call it in production** — it disrupts the JVM's own tuned heuristics and hurts performance.

## Memory Leaks (yes, even with GC)
A leak = memory that's no longer needed but **can't be collected because something still references it**. The GC isn't broken — your code is holding on.

**Common causes:** objects kept in a **`static` field / long-lived collection** and never removed · **listeners/callbacks** added but never unregistered · **caches/maps** that grow without bound.
```java
class MemoryLeakExample {
    private static List<Object> staticList = new ArrayList<>();   // static → lives whole program
    public void addToStaticList(Object obj) { staticList.add(obj); }  // never removed → never GC'd
}
// adding a million objects that stay referenced → heap grows → java.lang.OutOfMemoryError
```
- The objects can't be collected because `staticList` (a GC root via the static field) still references them. Classic long-running-server leak.

## Cyclic References
Two+ objects referencing each other in a loop:
```java
class Node { Node next; }
Node a = new Node();  Node b = new Node();
a.next = b;  b.next = a;   // cycle: a ↔ b
```
- **In Java this is NOT a leak.** Once `a` and `b` go out of scope, the *whole cycle* is unreachable from any GC root → reachability GC collects it. (Reference counting **would** leak here — that's its fatal flaw.)

---

## Best Practices
- **Don't null-out manually** — setting refs to `null` rarely helps the GC and clutters code; let scope handle it.
- **Minimize variable scope** — the sooner a reference goes out of scope, the sooner the object is eligible for GC.
- **Unregister listeners/callbacks** and bound your caches/maps to prevent leaks.
- **Avoid long-lived references** to short-lived data (especially in `static` fields/collections).

## Interview Q&A (memorize)
1. **Object lifecycle stages?** Creation → Usage → eligible for GC (unreachable) → Destruction (memory reclaimed).
2. **Stack vs heap?** Reference variable on the stack (dies with scope); object on the heap (lives until GC).
3. **When is an object eligible for GC?** When no live thread can reach it (out of scope, reassigned, or set to `null`).
4. **Does Java use reference counting?** No — **reachability** (Mark-Sweep-Compact from roots), which also collects cyclic references.
5. **Do cyclic references leak in Java?** No — reachability handles them; they'd only leak under reference counting.
6. **Does `System.gc()` force GC?** No — it's just a request the JVM may ignore; avoid in production.
7. **How do leaks happen despite GC?** Unwanted lingering references (static fields, growing collections, un-removed listeners).

## Pitfalls
- **"GC means no leaks"** — false; lingering references still leak → `OutOfMemoryError`.
- **Relying on `finalize()`** — deprecated, unpredictable timing, may never run; don't use it for cleanup (use try-with-resources / `AutoCloseable`).
- **Calling `System.gc()`** — harms performance, no guarantee it runs.
- **Manual `= null` everywhere** — usually pointless; trust scope and the GC.
- **Assuming destruction is immediate** — GC runs on the JVM's schedule; you don't control *when*.
