# Exception Handling in Java

> **One-liner:** A framework to catch runtime errors and keep the program running — wrap risky code in `try`, handle it in `catch`, clean up in `finally`.

**Trigger phrase:** *"`try` risky code → `catch` the exception → `finally` always cleans up; `throw` raises one, `throws` declares one; checked = compiler forces handling, unchecked = runtime/your-bug."*

---

## Core Idea
An **exception** is an unexpected event during execution that disrupts normal flow. Without handling, it **crashes the program** and skips all remaining code. Java's framework lets you **catch** it, react, and continue.
```java
int result = 10 / 0;      // ArithmeticException → program crashes here, nothing after runs
```
Wrap it and the program survives:
```java
try {
    int result = 10 / 0;                 // risky code
} catch (ArithmeticException e) {
    System.out.println("Division by zero!");   // handled
}
System.out.println("Program continues...");    // still runs
```

**Why it matters:** prevents crashes · separates error-handling from normal logic · eases debugging (stack traces) · guarantees resource cleanup (files/connections closed).

## The Exception Hierarchy (know this for interviews)
```
              Throwable
            /          \
        Error          Exception
     (JVM/system,    /          \
      don't catch)  checked    RuntimeException
                  (IOException,  (unchecked: NPE,
                   SQLException)  ArithmeticException, ...)
```
- **`Error`** — serious JVM problems (`OutOfMemoryError`, `StackOverflowError`); **don't catch**.
- **`Exception`** → split into **checked** (compiler-enforced) and **`RuntimeException`** = **unchecked** (your logic bugs).

## try / catch — handle the exception
`try` holds code that might fail; `catch` handles the matching exception type. Code after the block resumes normally.

**Multiple catch blocks** — handle different types; the **first matching** one runs:
```java
try {
    int[] arr = {1, 2, 3};
    System.out.println(arr[5]);     // ArrayIndexOutOfBoundsException thrown here
    int x = 10 / 0;                 // (never reached)
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Array index out of bounds!");
} catch (ArithmeticException e) {
    System.out.println("Division by zero!");
}
```
> **Order matters:** put **specific** exceptions before **general** ones — a `catch (Exception e)` before a specific type won't compile ("already caught"). You can't repeat the same type. Blocks can be **nested**.

**Multi-catch (Java 7+)** — one block, several types, via `|`:
```java
try { /* ... */ }
catch (IOException | SQLException e) { System.out.println("IO or DB problem"); }
```

## finally — always runs (cleanup)
Executes **whether or not** an exception was thrown (even on `return`) — ideal for closing resources.
```java
try {
    int result = 10 / 2;
    System.out.println("Result: " + result);
} catch (Exception e) {
    System.out.println("An error occurred.");
} finally {
    System.out.println("Finally always executes.");   // cleanup
}
```

**try-with-resources (Java 7+, preferred for cleanup):** auto-closes anything `AutoCloseable` — no manual `finally`:
```java
try (Scanner sc = new Scanner(new File("data.txt"))) {
    // use sc...
}   // sc.close() called automatically, even on exception
catch (FileNotFoundException e) { System.out.println("File not found!"); }
```

## throw vs throws
| | `throw` | `throws` |
|---|---------|----------|
| Purpose | **raise** an exception now | **declare** a method *may* throw |
| Where | inside a method/block | in the method **signature** |
| Takes | one exception **instance** | one or more exception **types** (comma-separated) |
| Example | `throw new IllegalArgumentException("bad");` | `void read() throws IOException, SQLException {}` |

**`throw`** — manually raise an exception (e.g. invalid input). The object must be a `Throwable` subclass:
```java
static void checkAge(int age) {
    if (age < 18)
        throw new IllegalArgumentException("Not eligible to vote.");  // unchecked → no throws needed
    System.out.println("Eligible to vote.");
}
```
> ⚠️ If you instead throw a **checked** type (`throw new Exception(...)`), the method **won't compile** unless it also declares `throws Exception` or catches it — that's the checked/unchecked rule in action.

**`throws`** — push handling responsibility to the **caller** (common for I/O/DB/network):
```java
static void divide() throws ArithmeticException {
    int result = 10 / 0;
}
public static void main(String[] args) {
    try { divide(); }
    catch (ArithmeticException e) { System.out.println("Handled: " + e); }
}
```
The exception **propagates up** the call stack until some caller catches it (or the JVM does → crash).

## Custom (user-defined) Exceptions
When built-in types don't describe your domain error, subclass `Exception` (checked) or `RuntimeException` (unchecked):
```java
class InsufficientBalanceException extends Exception {
    InsufficientBalanceException(String message) { super(message); }   // pass message up
}

class Main {
    public static void main(String[] args) {
        try {
            throw new InsufficientBalanceException("Balance too low!");
        } catch (InsufficientBalanceException e) {
            System.out.println("Caught: " + e.getMessage());
        }
    }
}
```
Gives meaningful, application-specific error reporting. Extend `RuntimeException` instead if callers shouldn't be forced to handle it.

## Checked vs Unchecked — the big distinction
| | **Checked** | **Unchecked** |
|---|-------------|---------------|
| Examples | `IOException`, `SQLException`, `FileNotFoundException` | `NullPointerException`, `ArithmeticException`, `ArrayIndexOutOfBounds` |
| Subclass of | `Exception` (not `RuntimeException`) | `RuntimeException` |
| Compiler check | **must** `try-catch` or declare `throws` — else **won't compile** | none — surfaces at **runtime** |
| Typical cause | external/recoverable (file, DB, network) | programming bug |
```java
// Checked → MUST handle or declare:
public static void main(String[] args) throws FileNotFoundException {
    Scanner sc = new Scanner(new File("test.txt"));   // compiler insists
}

// Unchecked → compiles fine, blows up at runtime:
int x = 10 / 0;     // ArithmeticException
```
> **Memory hook:** **Checked = compiler checks you** (external, recoverable). **Unchecked = your fault** (fix the code, don't catch).

## Interview Q&A (memorize)
1. **`throw` vs `throws`?** `throw` *raises* an exception (one instance, inside code); `throws` *declares* it (types, in the signature).
2. **Does `finally` always run?** Yes — even with `return` in try/catch. (Only `System.exit()` / JVM kill skips it.)
3. **Checked vs unchecked?** Checked = compiler forces handling (extends `Exception`); unchecked = runtime, optional (extends `RuntimeException`).
4. **Can `catch (Exception e)` come first?** No — general-before-specific won't compile; order specific → general.
5. **Custom exception — checked or unchecked?** Extend `Exception` to force callers to handle; `RuntimeException` to leave it optional.

## Pitfalls
- **Catch order** — broad `Exception` before a specific subtype = compile error.
- **Swallowing exceptions** — an empty `catch {}` hides bugs; at least log `e`.
- **Catching `Throwable`/`Error`** — never catch `Error` (OOM, stack overflow); the JVM can't recover.
- **Resource leaks** — closing in `try` (not `finally`/try-with-resources) skips cleanup when an exception hits; **prefer try-with-resources**.
- **Original-source gotcha:** `throw new Exception(...)` in a method with **no** `throws`/catch does **not** compile (it's checked) — use an unchecked type or declare it.
