# OOP — Index

30-second whole-topic recall. Read the **Trigger** and try to recall the **30-sec revision** before opening the note.

| # | Topic | Trigger phrase | 30-sec revision |
|---|-------|----------------|-----------------|
| 1 | [[1. Encapsulation]] | "private fields + public getters/setters/validation — outside world touches data only through a controlled interface" | Bundle data + its methods in one class; make fields **`private`**, expose **`public`** methods that gatekeep every read/write (so you can validate). **Principle** = hide internal state; **mechanism** = access modifiers + getters/setters. Wins: data security, flexibility (swap internals freely), modularity, easy debug/test. Pitfall: a blind setter for every field isn't encapsulation — add real logic; don't confuse with abstraction (hides *complexity*, not *data*). |
| 2 | [[2. Access Modifiers]] | "how far can this member be seen? — private (class) → default (package) → protected (package + subclasses) → public (everywhere)" | Four visibility levels, narrow→wide: **`private`** (same class) ⊂ **`default`**/no-keyword (same package) ⊂ **`protected`** (package **+ subclasses**, even other packages) ⊂ **`public`** (everywhere). Matrix columns Class/Package/Subclass/World: each step down drops one from the right, except `protected` adds Subclass back. Pitfalls: `protected` ≠ subclass-only (whole package too); blank ≠ public (it's package-private); matrix is Java-specific. |
| 3 | [[3. Inheritance]] | "child `extends` parent → inherits members for free, adds its own, can override; use on an 'is-a' relationship (Dog is-a Animal)" | Subclass `extends` superclass to **reuse / extend / override**. 3 types: **single** (A→B), **multilevel** (A→B→C), **hierarchical** (A→B, A→C). **No multiple class inheritance** in Java (→ Diamond Problem: ambiguous which parent's method); use **interfaces** instead. Riders: `protected` flows to children, **overriding** (same name+params+return, can't tighten access) → runtime polymorphism, **`super`** (parent member / `super(...)` constructor). Overload (same class, diff params, compile-time) ≠ override (parent↔child, same params, runtime). Pitfall: prefer **composition (has-a)** over forced inheritance; constructors aren't inherited. |
| 4 | [[4. Polymorphism]] | "same call, different behavior by context — resolved by argument types at compile-time (overload) or by actual object type at run-time (override)" | "Many forms," split by **when resolved**. **Compile-time/static** = method **overloading** (different params, picked by signature, early binding, faster, no inheritance needed; return type alone can't overload). **Run-time/dynamic** = method **overriding** (JVM dispatches on **actual object type, not reference type** — `Animal a = new Dog()` → Dog's method; needs inheritance, late binding). Pitfall: late binding only for overridden instance methods — `static`/`final`/`private` bind at compile time. C++ needs `virtual`; Java methods virtual by default, no operator overloading. |
| 5 | [[5. Abstraction]] | "focus on what an object does, not how — declare a contract via `abstract class` or `interface`, leave implementation to subclasses" | Hide the *how*, expose the *what*. Two tools: **abstract class** (can't instantiate; mixes abstract **+** concrete methods, instance fields, has constructor via subclass `super()`, single `extends`) and **interface** (pure contract; all methods `public abstract`, fields `public static final`, **multiple** `implements` → dodges Diamond; Java 8+ adds `default`/`static` methods). `default` methods = add to interfaces without breaking implementers (backward compat). Q&A: abstract class *can* extend another abstract class; *can* have a constructor but *can't* be instantiated. Pitfall: abstraction (hides complexity) ≠ encapsulation (hides data); prefer interface for pure contracts. C++ has no `interface` — use pure virtual (`=0`). |
