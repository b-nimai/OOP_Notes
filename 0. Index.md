# OOP — Index

30-second whole-topic recall. Read the **Trigger** and try to recall the **30-sec revision** before opening the note.

| # | Topic | Trigger phrase | 30-sec revision |
|---|-------|----------------|-----------------|
| 1 | [1. Encapsulation](1.%20Encapsulation.md) | "private fields + public getters/setters/validation — outside world touches data only through a controlled interface" | Bundle data + its methods in one class; make fields **`private`**, expose **`public`** methods that gatekeep every read/write (so you can validate). **Principle** = hide internal state; **mechanism** = access modifiers + getters/setters. Wins: data security, flexibility (swap internals freely), modularity, easy debug/test. Pitfall: a blind setter for every field isn't encapsulation — add real logic; don't confuse with abstraction (hides *complexity*, not *data*). |
| 2 | [2. Access Modifiers](2.%20Access%20Modifiers.md) | "how far can this member be seen? — private (class) → default (package) → protected (package + subclasses) → public (everywhere)" | Four visibility levels, narrow→wide: **`private`** (same class) ⊂ **`default`**/no-keyword (same package) ⊂ **`protected`** (package **+ subclasses**, even other packages) ⊂ **`public`** (everywhere). Matrix columns Class/Package/Subclass/World: each step down drops one from the right, except `protected` adds Subclass back. Pitfalls: `protected` ≠ subclass-only (whole package too); blank ≠ public (it's package-private); matrix is Java-specific. |
| 3 | [3. Inheritance](3.%20Inheritance.md) | "child `extends` parent → inherits members for free, adds its own, can override; use on an 'is-a' relationship (Dog is-a Animal)" | Subclass `extends` superclass to **reuse / extend / override**. 3 types: **single** (A→B), **multilevel** (A→B→C), **hierarchical** (A→B, A→C). **No multiple class inheritance** in Java (→ Diamond Problem: ambiguous which parent's method); use **interfaces** instead. Riders: `protected` flows to children, **overriding** (same name+params+return, can't tighten access) → runtime polymorphism, **`super`** (parent member / `super(...)` constructor). Overload (same class, diff params, compile-time) ≠ override (parent↔child, same params, runtime). Pitfall: prefer **composition (has-a)** over forced inheritance; constructors aren't inherited. |
| 4 | [4. Polymorphism](4.%20Polymorphism.md) | "same call, different behavior by context — resolved by argument types at compile-time (overload) or by actual object type at run-time (override)" | "Many forms," split by **when resolved**. **Compile-time/static** = method **overloading** (different params, picked by signature, early binding, faster, no inheritance needed; return type alone can't overload). **Run-time/dynamic** = method **overriding** (JVM dispatches on **actual object type, not reference type** — `Animal a = new Dog()` → Dog's method; needs inheritance, late binding). Pitfall: late binding only for overridden instance methods — `static`/`final`/`private` bind at compile time. C++ needs `virtual`; Java methods virtual by default, no operator overloading. |
| 5 | [5. Abstraction](5.%20Abstraction.md) | "focus on what an object does, not how — declare a contract via `abstract class` or `interface`, leave implementation to subclasses" | Hide the *how*, expose the *what*. Two tools: **abstract class** (can't instantiate; mixes abstract **+** concrete methods, instance fields, has constructor via subclass `super()`, single `extends`) and **interface** (pure contract; all methods `public abstract`, fields `public static final`, **multiple** `implements` → dodges Diamond; Java 8+ adds `default`/`static` methods). `default` methods = add to interfaces without breaking implementers (backward compat). Q&A: abstract class *can* extend another abstract class; *can* have a constructor but *can't* be instantiated. Pitfall: abstraction (hides complexity) ≠ encapsulation (hides data); prefer interface for pure contracts. C++ has no `interface` — use pure virtual (`=0`). |
| 6 | [6. Interface](6.%20Interface.md) | "a 100% abstract blueprint — abstract methods + constant fields only; a class signs the contract with `implements` and must fulfil every method; one class can sign many (→ multiple inheritance)" | Pure **contract**: declares *what*, never *how*. Fields are implicitly **`public static final`** constants (no instance vars); **no constructor**, can't be instantiated. Class uses **`implements`** and must define every method; a class can implement **many** interfaces → Java's safe multiple inheritance (dodges Diamond). Methods: `public abstract` by default, plus **`static`** (called on interface name, only touches static members) and **`default`** (has a body) since Java 8 — `default` lets interfaces gain methods **without breaking existing implementers** (backward compat). Interfaces can `extends` other interfaces to grow the contract. Wins: contract/consistency, loose coupling (program to interface), multiple inheritance of type. Pitfall: fields are silently constants; never `new` an interface; static methods aren't inherited. C++ → pure virtual (`=0`). |
| 7 | [7. Static Keyword](7.%20Static%20Keyword.md) | "belongs to the class, not the object — loaded once when the class loads; static methods/vars need no instance and can't touch non-static state directly" | `static` ties a member to the **class**, not any instance → **one copy**, shared by all objects, loaded **once** at class load, usable **without `new`**. **Static variable** = class variable shared across instances (the `count: 2` counter). **Static method** = call on the class name, no object; can only directly touch other static members (no `this`). **Static block** = runs once at class load, before any object/method, to init static vars (multiple blocks top-to-bottom). Static↔non-static: a static method reaches instance state only by `new`-ing an object. Wins: memory efficiency (one copy), utility/helper methods (`Math.sqrt()`), one-time init. Pitfall: shared-state surprises; `static` ≠ `final` (still mutable unless `static final`); don't overuse — it hurts testability. |
| 8 | [8. Inner Classes](8.%20Inner%20Classes.md) | "a class inside a class — 4 flavors (static nested / non-static inner / local / anonymous); static nested needs no outer instance, the rest do" | A class defined **inside** another, to group a helper used in one place; can reach outer members incl. `private`. **4 flavors:** **(1) Static nested** (`static class`) — **no outer instance**, sees only **static** outer members (e.g. `Map.Entry`). **(2) Non-static inner** (`class`, no static) — **tied to an outer object**, made via `outer.new Inner()`, sees **all** outer members. **(3) Local** — declared inside a method, scoped to it, sees outer members **+ effectively-final** locals (value is copied → must not change). **(4) Anonymous** — unnamed, declared+instantiated inline for a **one-off** interface/abstract impl (listeners, `Runnable`); Java 8 **lambdas** replace single-method ones. Memory hook: only **static nested** is independent; the other 3 cling to an instance/scope. Pitfall: non-static inner holds a **hidden outer reference** → memory leaks (prefer static nested when no instance data needed); `outer.new Inner()` syntax for non-static, `new Outer.Nested()` for static. |
| 9 | [9. Relationships Between Classes](9.%20Relationships%20Between%20Classes.md) | "has-a strength scale: association (general link) → aggregation (has-a, independent lifecycle) → composition (part-of, shared lifecycle — destroy whole, parts die)" | How classes connect (`has-a`, not `is-a`), on a **strength/ownership scale**. **Association** = general link, no ownership, both independent; multiplicity **1-1 / 1-many / many-many** (Teacher↔Student, Person↔Passport). **Aggregation** = "has-a", **weak**: whole holds parts **passed in from outside**, parts **outlive** the whole (Department ◇ Employee). **Composition** = "part-of", **strong**: whole **creates parts internally** & **owns** them, parts **die with** the whole (House ◆ Room, Car ◆ Engine). **Lifecycle test:** destroy whole → parts survive? **Yes = aggregation, No = composition**. **Creation tell:** passed in = aggregation, `new`-ed inside = composition. UML: hollow ◇ aggregation, filled ◆ composition. A class can do several at once (Library ◇ Book, Book ◆ Chapter). Pitfall: both hold references — ownership of **lifecycle** decides, not "holds a list"; all are `has-a`, don't use inheritance. Favor **composition over inheritance**. |
| 10 | [10. Object Cloning](10.%20Object%20Cloning.md) | "copy an object: implement `Cloneable`, override `clone()`. Default `super.clone()` = shallow (nested refs shared); deep clone = also clone every nested object yourself" | Make an independent copy (same data, **new memory address**). Wiring: **`Cloneable`** = **marker interface** (no methods, just permits cloning — skip it → `CloneNotSupportedException`) + **`Object.clone()`** (`protected`, override it; default = shallow). **Shallow** (`super.clone()`): primitives/Strings copied, but **reference fields share the same nested object** → mutate clone's nested obj, original changes too (the "New Delhi" trap). **Deep**: every nested object cloned too → fully independent; `super.clone()` only goes one level, so **clone nested objects yourself** (each nested class must override `clone()`). Memory hook: **shallow = share, deep = duplicate**; if all fields are primitive/immutable, shallow already = deep. Uses: undo/redo snapshots, caching, Prototype pattern. Better alternatives: **copy constructor** / serialization round-trip (Bloch: `clone()` is flawed). Pitfall: `clone()` **bypasses constructors** (no validation); deep clone needs *every* level to cooperate. |
| 11 | [11. Exception Handling in Java](11.%20Exception%20Handling%20in%20Java.md) | "`try` risky code → `catch` the exception → `finally` always cleans up; `throw` raises one, `throws` declares one; checked = compiler forces handling, unchecked = runtime/your-bug" | Catch runtime errors, keep running. **Hierarchy:** `Throwable` → `Error` (JVM, don't catch) + `Exception` → **checked** (`IOException`/`SQLException`) & `RuntimeException` = **unchecked** (NPE, ArithmeticException). **`try`** = risky code, **`catch`** = handle (multiple blocks, **specific→general** order or won't compile; multi-catch `IOException \| SQLException`), **`finally`** = always runs (cleanup, even on `return`); **try-with-resources** auto-closes `AutoCloseable`. **`throw`** = raise an exception instance *now* (inside code); **`throws`** = declare types in the *signature*, pushing handling to the caller (exception **propagates up** the stack). **Custom exception** = subclass `Exception` (forces handling) or `RuntimeException` (optional). **Checked vs unchecked:** checked = compiler forces try/catch-or-throws (external/recoverable); unchecked = runtime, optional (your bug) → memory hook "**checked = compiler checks you, unchecked = your fault**". Pitfall: empty `catch{}` swallows bugs; never catch `Error`; `throw new Exception()` w/o `throws` won't compile. |
