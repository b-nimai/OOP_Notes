# Relationships Between Classes

> **One-liner:** How classes connect to model a system — **association** (uses-a / knows-a), and its two "has-a" specializations **aggregation** (weak, parts outlive the whole) and **composition** (strong, parts die with the whole).

**Trigger phrase:** *"has-a strength scale: association (general link) → aggregation (has-a, independent lifecycle) → composition (part-of, shared lifecycle — destroy whole, parts die)."*

---

## Core Idea
Beyond **inheritance** (`is-a`), objects collaborate via **`has-a`** relationships. The three sit on a **strength/ownership scale**:

```
weaker bond ───────────────────────────────► stronger bond
Association        ⊃   Aggregation        ⊃   Composition
"knows-a/uses-a"       "has-a" (weak)          "part-of" (strong)
just a link            owns but parts free     owns + parts die with it
```

> **Memory hook (lifecycle test):** "If I destroy the whole, do the parts survive?" **Yes → Aggregation. No → Composition.** No ownership at all → just Association.

| Relationship | Bond | Ownership | Part's lifecycle | Real-world |
|--------------|------|-----------|------------------|------------|
| **Association** | general | none | independent | Teacher ↔ Student |
| **Aggregation** | weak (has-a) | holds, doesn't own | **independent** of whole | Department ◇ Employee |
| **Composition** | strong (part-of) | owns | **dies with** whole | House ◆ Room, Car ◆ Engine |

*(UML hint: aggregation = hollow diamond ◇, composition = filled diamond ◆ — filled = "filled-in/permanent" = dies together.)*

---

## 1. Association — "knows-a / uses-a"
Two classes are simply **linked** — objects of one interact with objects of another via a reference. No ownership; both are independent. Implemented with references/collections.

**Multiplicity (how many on each side):**
- **One-to-One** — `Person` ↔ `Passport` (one each).
- **One-to-Many** — one `Teacher` → many `Student`s.
- **Many-to-Many** — `Student`s ↔ `Course`s (each student many courses, each course many students).
```java
class Teacher {
    private String name;
    public Teacher(String name) { this.name = name; }
}

class Student {
    private String name;
    private Teacher teacher;            // just a reference — a link, no ownership
    public Student(String name, Teacher teacher) {
        this.name = name;
        this.teacher = teacher;
    }
}
```

## 2. Aggregation — "has-a" (weak, independent)
A **whole-part** relationship where **part can exist without the whole**. The whole *holds* references it didn't create; deleting the whole leaves the parts alive. The part is usually **passed in** from outside.
```java
class Employee {
    private String name;
    public Employee(String name) { this.name = name; }
}

class Department {
    private List<Employee> employees;          // holds employees...
    public Department(List<Employee> employees) {
        this.employees = employees;            // ...but they're created OUTSIDE & passed in
    }
}
```
Delete the `Department` → the `Employee` objects still exist (they can move to another department).

**Characteristics**
- **Independent lifecycle** — part is not owned by the whole.
- **Weaker bond** — parts are typically shared / supplied externally.

## 3. Composition — "part-of" (strong, shared lifecycle)
A stricter aggregation: the whole **owns** its parts and **creates them internally**. If the whole dies, the parts die with it. The part has no meaningful existence on its own.
```java
class Room {
    private String name;
    public Room(String name) { this.name = name; }
}

class House {
    private List<Room> rooms;
    public House() {
        rooms = new ArrayList<>();
        rooms.add(new Room("Living Room"));    // created INSIDE — owned by the House
        rooms.add(new Room("Bedroom"));
    }
}
```
Destroy the `House` → its `Room`s cease to exist.

**Characteristics**
- **Dependent lifecycle** — part lives and dies with the whole.
- **Stronger bond** — parts are created and owned internally.

> **Aggregation vs Composition — the tell:** *who creates the part?* Passed in from outside → **aggregation**. `new`-ed inside the whole → **composition**.

---

## A class can hold several relationships at once
Real systems mix them:
- A `Library` **aggregates** `Book`s (books survive without the library).
- A `Book` **composes** `Chapter`s (chapters vanish if the book is destroyed).

## Why it matters (design impact)
- **Models reality accurately** → cleaner, more maintainable design.
- **Composition over inheritance** — favoring `has-a` over `is-a` gives flexible, loosely-coupled code (swap parts at runtime) without inheritance's rigidity. (See [3. Inheritance](3.%20Inheritance.md).)

## Interview Q&A (memorize)
1. **Aggregation vs Composition?** Both are "has-a"; in **composition** the part's lifecycle is **bound** to the whole (created inside, dies with it), in **aggregation** it's **independent** (passed in, outlives the whole).
2. **Quick test to tell them apart?** "Destroy the whole — do parts survive?" Yes = aggregation, No = composition.
3. **Association vs Aggregation?** Aggregation is a *specialized* association implying a **whole-part / has-a** ownership flavor; plain association is just a link with no ownership.
4. **UML symbols?** Hollow diamond ◇ = aggregation, filled diamond ◆ = composition (on the *whole* side).

## Pitfalls
- **Treating aggregation = composition.** The difference is **lifecycle ownership**, not just "one class holds another."
- **All three are `has-a`/links, not `is-a`.** Don't reach for inheritance to model them.
- **"Whole holds a list" doesn't decide it.** Both aggregation and composition hold references — what matters is **who owns the part's lifecycle**.
- **Real boundaries can be fuzzy.** The same pair can look like aggregation or composition depending on the domain — judge by whether the part should outlive the whole.
