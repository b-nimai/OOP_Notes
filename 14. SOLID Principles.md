# SOLID Principles

> **One-liner:** Five design guidelines (Robert C. Martin) for OOP that keep code **modular, flexible, and maintainable** — each class does one job, you extend rather than edit, subtypes stay substitutable, interfaces stay small, and code depends on abstractions.

**Trigger phrase:** *"SOLID = **S**ingle responsibility (one reason to change) · **O**pen/closed (extend, don't modify) · **L**iskov (subtype substitutable for base) · **I**nterface segregation (small focused interfaces) · **D**ependency inversion (depend on abstractions, inject them)."*

---

## Core Idea
**SOLID** is an acronym for five principles that make object-oriented code easier to change without breaking it. They're not syntax — they're **design discipline**: follow them and a codebase stays loosely coupled, testable, and open to new features; ignore them and small changes ripple everywhere.

| | Principle | In one line |
|---|-----------|-------------|
| **S** | Single Responsibility | one class, **one reason to change** |
| **O** | Open/Closed | **open** to extension, **closed** to modification |
| **L** | Liskov Substitution | a subtype must work **anywhere its base** is expected |
| **I** | Interface Segregation | many **small** interfaces beat one fat one |
| **D** | Dependency Inversion | depend on **abstractions**, not concretions |

> **The thread tying them together:** reduce coupling and isolate change. O, L, I, D all lean on **abstraction + polymorphism** (interfaces/abstract classes) — see [Abstraction](5.%20Abstraction.md), [Interface](6.%20Interface.md), [Polymorphism](4.%20Polymorphism.md).

## S — Single Responsibility Principle (SRP)
**A class should have only one reason to change** → one job. Mixing responsibilities means a change to one drags in bugs in the other.
```java
// ✗ one class doing two jobs
class Employee { double calculateSalary() {...}  void generateReport() {...} }

// ✓ split — salary changes can't break reporting
class SalaryCalculator { double calculateSalary(Employee e) {...} }
class ReportGenerator  { void   generateReport(Employee e) {...} }
```
- **Test:** "Can I describe this class without using *and*?" If not, split it.

## O — Open/Closed Principle (OCP)
**Open for extension, closed for modification** → add behavior by adding **new** code, not editing tested code. Achieved via abstraction + polymorphism.
```java
abstract class Shape { abstract double calculateArea(); }
class Rectangle extends Shape { double calculateArea() { return length * breadth; } }
class Circle    extends Shape { double calculateArea() { return Math.PI * radius * radius; } }
// Add Triangle later → just `extends Shape`; no existing class is touched.
```
- **Smell it violates:** an `if/else` or `switch` on a type that grows every time you add a case → replace with polymorphism.

## L — Liskov Substitution Principle (LSP)
**A subclass must be usable anywhere its parent is, without surprising the caller.** If substituting the subclass breaks behavior, the inheritance is wrong.
```java
// ✗ Penguin is-a Bird, but can't fly → throws at runtime where a Bird is expected
class Bird    { void fly() {...} }
class Penguin extends Bird { void fly() { throw new UnsupportedOperationException(); } }

// ✓ separate the capability — only flying birds implement it
interface FlyingBird { void fly(); }
class Sparrow implements FlyingBird { public void fly() {...} }
class Penguin { /* simply doesn't implement FlyingBird */ }
```
- **Test:** a subclass that **overrides a method to throw, return null, or do nothing** is usually an LSP violation.

## I — Interface Segregation Principle (ISP)
**Don't force a class to implement methods it doesn't need.** Prefer several small, role-specific interfaces over one fat one.
```java
// ✗ fat interface → Robot forced to fake eat()
interface Worker { void work(); void eat(); }
class Robot implements Worker { public void eat() { throw new UnsupportedOperationException(); } ... }

// ✓ split by capability
interface Workable { void work(); }
interface Eatable  { void eat(); }
class Human implements Workable, Eatable { ... }
class Robot implements Workable { ... }   // no pointless eat()
```
- ISP is OCP/LSP's cousin at the **interface** level: empty/throwing method bodies are the tell.

## D — Dependency Inversion Principle (DIP)
**High-level modules and low-level modules should both depend on abstractions**, not on each other. Don't `new` concretions inside a class — **inject** the abstraction.
```java
// ✗ Computer hard-wired to one concrete keyboard
class Computer { private WiredKeyboard keyboard = new WiredKeyboard(); }

// ✓ depend on an interface, pass it in (dependency injection)
interface Keyboard { void connect(); }
class WiredKeyboard    implements Keyboard { public void connect() {...} }
class WirelessKeyboard implements Keyboard { public void connect() {...} }
class Computer {
    private Keyboard keyboard;
    Computer(Keyboard keyboard) { this.keyboard = keyboard; }   // injected → swap freely
}
```
- **Dependency Inversion** (the principle) is *enabled by* **Dependency Injection** (the technique of passing dependencies in via constructor/setter).

## Interview Q&A (memorize)
1. **What does SOLID stand for?** SRP, OCP, LSP, ISP, DIP (and who: Robert C. Martin / "Uncle Bob").
2. **SRP in one sentence?** A class should have **one reason to change** — a single responsibility.
3. **How do you satisfy OCP?** Program to an abstraction (interface/abstract class) and add new subclasses instead of editing existing code.
4. **Classic LSP violation?** `Penguin extends Bird` overriding `fly()` to throw — it can't substitute a `Bird`.
5. **ISP vs SRP?** SRP = one class, one job; ISP = one interface, one role (don't force unused methods).
6. **DIP vs Dependency Injection?** DIP = the *principle* (depend on abstractions); DI = the *technique* (inject the dependency) used to achieve it.

## Pitfalls
- **Over-splitting (SRP)** — shattering everything into one-method classes adds complexity; "one reason to change," not "one line."
- **LSP looks fine at compile time** — violations surface at **runtime** (thrown exceptions, wrong results); inheritance compiling ≠ correct.
- **Fat interface creep (ISP)** — interfaces accrete methods over time; watch for implementers with empty/throwing bodies.
- **`new` inside a class (DIP)** — hard-coding a concrete dependency makes it untestable (can't mock); inject instead.
- **Cargo-culting** — SOLID guides design; don't add abstraction layers "for SOLID" where a simple class suffices (YAGNI).
